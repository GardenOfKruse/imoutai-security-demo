# 教程：梆梆加固 App 的运行态分析与签名还原实操

> 以 i茅台 v1.9.12（com.moutai.mall）为实例，2026-09 授权本地研究产出。
> 面向：授权安全研究同事。所有操作限于自有 root 设备 + 本地样本 + 防御建议产出场景。
> 配套脚本：`case-studies/imoutai/hooks/`；数据：`work/20260907-222238-i-app-frida-dump-dex-android-apk/`

---

## 0. 一句话方法论

**打不穿壳，就绕开壳。** 不要在进程内和加固对抗（解密、反调试、自检），等壳把业务代码解密加载完成后，用"延迟附加 + 纯反射 + 只读观测"直接读运行态——拿接口定义、请求模型、签名调用链、头部常量，全程不需要 dex 文件本体。

传统路线（spawn 注入 → 压反调试 → 内存扫 dex dump）在这个样本上**全部失败**（见 §3），而新路线两次会话就拿到了登录接口全貌和签名公式。

## 1. 环境基线

| 组件 | 要点 |
|---|---|
| 设备 | 真机 root（Magisk/Kitsune，自带 root 隐藏）。模拟器会被 `libemulator_check.so` 秒杀 |
| frida-server | **改名**（如 `/data/local/tmp/fs`）+ **非默认端口**（8899）+ `adb forward tcp:8899 tcp:8899`。默认 27042 会被端口扫描检测 |
| frida 版本 | PC 与设备端**必须一致**（本例 17.11.0） |
| frida 17 三坑 | ① 内置 Java API 已移除，agent 里 `import Java from 'frida-java-bridge'` 需 esbuild 打包（见 §8 流水线）；② RPC 导出方法名 **camelCase**（`getStats`，snake_case 报 "unable to find method"）；③ `Memory.readByteArray` 已移除，用 `ptr.readByteArray()` |
| 反编译 | jadx 1.5.5（壳代码仍可反编译，用于看 stub 类） |

## 2. 静态侦察：10 分钟定性壳类型

解包 APK（`unzip`）看四个特征即可定性：

```
lib/arm64-v8a/libDexHelper.so      ← SecShell 壳本体（字符串全加密）
lib/arm64-v8a/libdexvmp.so         ← DexVMP 方法虚拟化
assets/RiskStub.dex + libRiskStub.so ← Everisk 风控 SDK
assets/meta-data/manifest.mf + rsa.sig ← 完整性自校验
```

再反编译 Manifest 看 Application：`com.secneo.apkwrapper.AW` = 梆梆 StubApplication 实锤。
jadx 里业务包（如 `com.moutai.mall`）只剩 `R.java`/`IsoService.java` → **全加密壳**，业务 dex 运行时才解密 → 静态路线死刑，直接进动态。

## 3. 失败路线速览（为什么放弃 spawn 脱壳，别重复踩）

| 路线 | 结果 | 根因 |
|---|---|---|
| spawn 注入 + 反调试压制 | 壳按名加载 `libDexHelper.so` 失败（linker namespace）→ 手工改实参让 ART 加载成功 → `JNI_OnLoad` 内自检 abort | 壳加载期自检（扫 maps/上下文校验），注入态必挂 |
| 干净进程全内存扫 dex（4 轮共 ~1000 区域） | 0 个完整 dex | 业务 dex **按需解密、读后回密**（SIGSEGV fault handler 按需解密假设） |
| frida-dexdump | 挂起无输出 | 与该壳不兼容 |
| kill -STOP 冻结快照 | 父进程立刻被杀 | 壳 fork 独立看门狗子进程（app_process64 nanosleep 循环） |
| 手工 dlopen + JNI_OnLoad | FindClass boot classloader 失败 SIGSEGV | 手工调用缺 ART 上下文 |

结论：**进程内对抗 = 高成本低收益**。壳的设计目标就是让这些路线失败，但它的设计没有覆盖"运行态反射读取"这个面——这就是 §4 的突破口。

## 4. 核心手法：延迟附加 + 纯反射 dump（本教程精华）

**原理**：壳解密完成后，业务类就在 ART 里活着。`enumerateLoadedClassesSync` + `getDeclaredMethods/Annotations/Fields` 拿到的是完整的方法签名和注解——Retrofit 注解里直接写着 `@POST("/xhr/front/user/register/login")`。**不需要方法体**：接口定义、参数表、序列化方式全在注解和字段里。

**操作时序**（脚本 `hooks/obs-driver.py` + `hooks/_build/entry-annot2.js`）：

```bash
adb shell am start -n <pkg>/.module.splash.SplashActivity   # 正常启动，不注入
# sleep 2~6s —— 等壳完成解密加载
python obs-driver.py --js dump-dex-hook-annot2.js --out <out> --attach-running
```

agent 侧（纯只读，零 hook，最小足迹）：

```js
Java.perform(function () {
    Java.enumerateLoadedClassesSync()
        .filter(n => n.indexOf('com.moutai.mall') === 0)   // 目标包名过滤
        .sort(priorityFirst)                                // login/auth/api 类优先
        .forEach(name => {
            const cls = Java.use(name).class;
            const methods = cls.getDeclaredMethods();       // 方法签名
            for (m of methods) {
                m.getDeclaredAnnotations();                 // @POST/@GET/@Body...
                m.getParameterAnnotations();                // @HeaderMap/@Query...
            }
            cls.getDeclaredFields();                        // 请求模型字段
            send({type: 'reflection', className: name, ...}); // 每类一发，落袋为安
        });
});
```

**实测战果**：220 个业务类 0 失败；117 个 Retrofit 方法含完整 URL；请求模型字段（`LoginRequest{mobile,vCode,ydLogId,ydToken}`）、Moshi 序列化、`@hj.j()=HeaderMap` 全部现形。

关键工程细节：
- **目标类优先排序**：进程随时可能死，先 dump login/auth/api 再补全量
- **每类独立 send**：driver 侧落 jsonl，进程死了已收的不丢
- **bundle 越小越好**：460KB 全功能 bundle 加载窗口内易被杀，精简到只做反射

## 5. 绕过"设备异常"熔断：不对抗，快进快出

**现象**：Everisk 检测到 root 环境后，不立即杀——启动一个 ~30-48 秒的倒计时（隔离进程 `:rs` 的 IsoService 里 `Thread.sleep` 循环计数），到点先 SIGSEGV 自毁再杀主进程。**与是否注入无关**（干净启动也死），是环境检测不是注入检测。

**应对策略**：
1. 不去 patch `System.exit`/`Process.killProcess`（能拦 2 次，native 兜底拦不住）；
2. **所有采集动作压缩进窗口**：T+4~6s 附加 → T+25s 前完成 dump/采样 → 主动 detach；
3. 每次实验独立输出目录 + 增量落盘，进程死了数据还在；
4. attach 失败率 ~50%，**重试即可**——注意先区分失败原因（见 §7 坑）。

另一个我们观察到的检测维度：root 检测（`/proc/self/cmdline`、`su`、KernalSU 字符串）、frida 特征（maps 扫描、memfd 名、27042 端口——所以改名+改端口+晚附加）。**熔断时长反而是这个壳最有效的防线**——但它防不住"快进快出"。

## 6. 运行时采样：反射调用纯工厂方法（拿到签名输入输出的关键）

拿签名算法的完整链条（三步，全程零网络请求）：

**Step 1 — 区分纯工厂方法。** 反射 dump 后在 LoginActivity 找到 `getVerifyRequest(String): GetVerifyCodeRequest`。判断它是"纯本地工厂"（只构造对象，不发网络）：方法返回请求对象、无回调/协程 launch。**纯工厂可以安全地本地调用**——这不算"向服务器发请求"。

**Step 2 — 活实例 + 构造器 hook 采样。** 用 `Java.choose` 拿堆上的活 Activity 实例，喂合成手机号：

```js
Java.choose('com.moutai.mall.module.login.LoginActivity', {
    onMatch: function (inst) {
        const req = inst.getVerifyRequest(Java.use('java.lang.String').$new('13000000001'));
        // req.md5 / req.timestamp / req.mobile → 三元组
    },
    onComplete: function () {}
});
```

同时 hook 请求模型的 `$init` 构造器，构造瞬间参数自动落网。每调用一次得一个 `(mobile, timestamp, md5)` 样本，timestamp 每次 +500ms（真实时钟）。

**Step 3 — MessageDigest 输入捕获（一锤定音）。** 字典猜盐不可靠（我们猜了 60 组合全挂）。直接 hook 哈希 API，在采样调用期间开捕获窗口：

```js
let capturing = false;
Java.use('java.security.MessageDigest').update.overloads.forEach(ov => {
    ov.implementation = function () {
        if (capturing) captureBytes(arguments);   // byte[] → hex
        return ov.apply(this, arguments);
    };
});
// digest() 同理；字节转 hex：遍历 length + 索引，arg[i] & 0xff
```

采样时 `capturing=true` → 调 `getVerifyRequest` → `capturing=false`。**明文拼接串直接现形**：

```
update 输入 = "2af72f100c356273d46284f6fd1dfc08" + "13000000001" + "1789140362120"
digest 输出 = md5 字段值 → 离线复算 15/15 逐字节 PASS
```

调用链（栈回溯）同时归因了实现类：`LoginActivity.getVerifyRequest → com.netease.libs.yxsecurity.encrypt.CryptoUtil.l → o → MessageDigest(MD5)`。

**工程细节**：byte[] 参数读取用 `arg.length + arg[i] & 0xff`（`$className` 判断在某些版本不可靠）；多段 update 可能存在（每段都收）；同一窗口内可能有其他线程的哈希调用，用"输入串包含 mobile"过滤。

## 7. 常见坑（血泪清单）

1. **attach 后崩 `art::OatDexFile::FindClassDef+52` 空指针** → 不是壳检测，是设备/zygote 状态问题，**重启手机**即恢复（实测两次）。别错误归因后放弃路线。
2. **Splash 卡隐私弹窗**，堆上永远没有目标 Activity 实例 → 直接 `su -c 'am start <pkg>/.module.login.LoginActivity'` 拉起，`dumpsys activity top | grep <pkg>` 确认在顶层再采样。
3. **frida-java-bridge 打包**：`require("buffer")` 残留会报 `require is not defined`——用 `--alias:buffer=<shim>` 显式替换，产物 grep 校验。
4. **RPC 大小写**：frida 17 导出名 camelCase。
5. **`--out` 目录非空即拒**：driver 强制，防止覆盖证据。
6. **时间预算**：单会话 10 分钟没新证据就停，记录失败，别无限重试。

## 9. 防御视角（产出给开发方的核心结论）

1. 全加密壳的物理上界：解密后必进内存，反射读取不可防——**关键逻辑下沉 native + 服务端校验**才是治本；
2. 签名构造集中在单个 Java 工厂方法（一次反射调用即可批量采样）→ 拆散调用链、每会话服务端下发签名盐；
3. `md5(key+mobile+ts)` 无盐无 HMAC 无 nonce → 应换 HMAC-SHA256 + 服务端时间窗 + nonce 防重放；
4. RSA 私钥运行时无校验可导出（`CryptoUtil.getPrivateKey()`）→ 私钥应每会话协商；
5. 客户端熔断自杀只对抗"长驻注入"，防不了快进快出 → 风控信号上报服务端聚合判定。
