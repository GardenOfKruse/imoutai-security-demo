## 1. 已证实的因果链（本轮 mp21→mp23→干净进程实验）

1. 壳 `AW.attachBaseContext` → `System.loadLibrary("DexHelper")` → 按名 `nativeLoad(libDexHelper.so)` 在本设备**失败**（namespace 解析不到）→ natives 未注册 → `com.secneo.apkwrapper.H.is(int)` 抛 UnsatisfiedLinkError → 主线程死 → **业务类永远=0**（此前所有 spawn 注入会话业务类为 0 的总根因）
2. mp23 修正（nativeLoad 实参改绝对路径 + loader 参数换 app PathClassLoader）后：`dlopen_ext(libDexHelper.so) ret=ok` **壳库成功加载**；但随后 `JNI_OnLoad` 内 FindClass 触发 ART abort（"No pending exception expected"，栈在 LoadNativeLibrary→FindClass）。判定：JNI_OnLoad 内部的前置调用失败（可能是 maps 扫 frida 或 loader 身份自检），失败路径异常处理不干净导致 abort。**进程内注入路线在此壳的加载期自检处受阻**
3. mp23 主进程死后系统**干净重启**（无注入）：新进程完整走通壳初始化——libDexHelper 已映射、`LoginActivity` resumed（**业务 dex 已解密加载进内存的实证**）
4. 对干净进程 `kill -STOP` 冻结 → **壳 fork 的看门狗子进程**（独立 app_process64，nanosleep 循环）检测到父进程异常态后 SIGKILL 父进程 → 冻结快照法失败
5. **不冻结、纯只读 `/proc/PID/mem` dd 抓取：进程无感知，两次全量抓取后进程仍存活** ✅ —— 这是既绕开注入检测、又绕开看门狗的可行通道
6. 当前 memdump2.sh 的 bug：case 通配 `\[*]` 匹配不了带空格的 `[anon:dalvik-main space (region space)]`（read 分词后 f6=`[anon:dalvik-main` 无 `]`）→ **dalvik 堆（dex 所在）从未被抓到**，这就是两次快照只有 ~6.5MB、carve 出 0 dex 的原因
